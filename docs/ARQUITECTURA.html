Visión general

Qué resuelve Argos y cómo se compone a alto nivel.

Argos se monta sobre un stack de observabilidad open-source (Prometheus, Loki, Grafana, Alertmanager) y le suma una capa de inteligencia: cuando una alerta por umbral se dispara, un workflow en n8n consulta una base de conocimiento vectorial (Qdrant + RAG), pide a un LLM (Gemini o Claude) una síntesis del problema con pasos de resolución, envía la notificación enriquecida por email y, si el incidente es nuevo, lo auto-documenta de vuelta en la base. Todo se opera desde un dashboard propio (React+Vite) que habla con una API .NET 10 (rag-api), la cual además ejecuta pruebas de carga k6 on-demand y consulta métricas/logs reales. El despliegue es 100% Docker, orquestado por un docker-compose raíz que incluye 3 stacks sobre una red compartida argos-net.

Flujos clave (end-to-end)

Los tres recorridos que definen el valor de la plataforma.

① Detección → Diagnóstico IA → Notificación

Tráfico/ataque llega a nginx → Prometheus/Loki evalúan reglas → Alertmanager enruta las alertas de incidente al webhook de n8n → n8n consulta RAG (rag-api /query sobre Qdrant) → arma prompt y pide a Gemini/Claude síntesis + pasos → envía email enriquecido. El resto de alertas salen por email tradicional desde Alertmanager (sin doble notificación).

② Auto-documentación de incidentes nuevos

En el mismo workflow, la rama «¿Es nuevo?» detecta incidentes sin match en la base → genera el documento con el LLM → hace POST rag-api /upsert → queda embebido en Qdrant y visible en la vista Base de Conocimiento del dashboard (estados documentado_previamente / auto_documentado).

③ Pruebas de carga k6 on-demand (solo Admin)

Desde la vista Pruebas de Carga, rag-api lanza el contenedor grafana/k6 como hermano vía Docker socket (volúmenes argos_k6_scripts/argos_k6_results) → k6 golpea a nginx con 3 escenarios (normal/spike/ataque) → el de ataque dispara 4 alertas Loki → reactiva el flujo ① → los resultados se persisten en Qdrant (argos_loadtests).

Servicios y puertos

Catálogo de contenedores por stack, con su puerto expuesto y rol.

argos-dashboard :3001

SPA React+Vite+TS (7 vistas). nginx sirve estáticos y proxya /api → rag-api.

rag-api :8000

.NET 10 (Argos API): JWT, CRUD, /incidents, /query, /observability, /loadtests. Núcleo del backend.

n8n :5678

Orquestación del workflow Alert Analysis (webhook → RAG → LLM → email → auto-doc).

Qdrant :6333

Vector DB. Colecciones incidentes y argos_loadtests. Embeddings 384-dim.

Prometheus :9090

Métricas + 13 reglas de alerta. Scrapea exporters y evalúa umbrales.

Loki :3100

Agregación de logs + 5 reglas LogQL. Recibe push desde Alloy.

Alertmanager :9093

Routing de alertas: webhook n8n (incidentes) / email (resto).

Grafana :3000

3 dashboards provisionados. Datasources Prometheus + Loki.

nginx-proxy :80/:8443

Reverse proxy + borde de tráfico. Sus logs alimentan a Alloy/Loki.

Alloy :12345

Colector de logs (sucesor de Promtail) → push a Loki.

Exporters :9100/9113/8080

node-exporter, nginx-exporter, cAdvisor — fuentes de métricas.

MembresiaAPI :5000

API .NET 10 Minimal de demo. Genera tráfico y logs realistas.

SQL Server :1433

MembresiaDB (esquema + SP + seed idempotente vía db-init).

grafana/k6 on-demand

Contenedor efímero lanzado por rag-api para las pruebas de carga.

Despliegue

Un compose raíz incluye los 3 stacks sobre una red externa compartida.

🌐 argos-net

Red bridge externa creada una vez (docker network create argos-net). Todos los stacks la declaran external: true para comunicarse entre sí.

📦 docker-compose raíz

include: de monitoring + apps + proxy. Un solo docker compose up -d --build levanta toda la plataforma.
